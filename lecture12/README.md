# Лекція №12 Продуктивність і паралелізм

## Контрольні запитання

### 1. Що таке конвеєрне виконання і яке теоретичне прискорення воно дає?
**Конвеєрне виконання (pipelining)** — це техніка організації обробки інструкцій у процесорі, при якій виконання кожної команди розбивається на кілька послідовних стадій (наприклад: *Fetch, Decode, Execute, Memory, Write-back*), і різні стадії конвеєра обробляють кілька команд одночасно на кожному такті.  
**Теоретичне прискорення:**  
За ідеальних умов (за відсутності конвеєрних конфліктів) конвеєр із $N$ стадіями дозволяє наблизитися до **$N$-кратного прискорення** (тобто пропускна здатність наближається до виконання однієї команди за такт, $CPI \approx 1$).

### 2. Наведіть приклади структурного конфлікту, конфлікту за даними і за керуванням.
* **Структурний конфлікт (Structural Hazard):** Виникає при браку апаратних ресурсів.  
  *Приклад:* Дві команди на різних стадіях (наприклад, *Fetch* для нової команди і *Memory* для команди `LOAD`) одночасно звертаються до єдиного спільного порту/блоку оперативної пам'яті.
* **Конфлікт за даними (Data Hazard):** Виникає, коли наступна команда залежить від результату попередньої, який ще не записаний у регістр.  
  *Приклад:*  
  `ADD R1, R2, R3`  
  `SUB R4, R1, R5` *(команда `SUB` потребує значень $R1$, які `ADD` обчислить тільки на стадії Execution і запише на стадії Write-back)*.
* **Конфлікт за керуванням (Control Hazard):** Виникає при виконанні команд розгалуження (умовних/безумовних переходів).  
  *Приклад:*  
  `BEQ R1, R2, target_label` *(конвеєр уже завантажує наступні за порядком інструкції, хоча результат порівняння $R1$ і $R2$ ще не обчислено)*.


### 3. Чим суперскалярне виконання відрізняється від простого конвеєра?
* **Простий (однопотоковий) конвеєр:** На кожну стадію конвеєра за один такт вибирається і передається **лише одна** команда (1-way).
* **Суперскалярне виконання (Superscalar execution):** Процесор має кілька паралельних виконавчих пристроїв (декілька АЛП, блоків завантаження тощо) і здатен вибирати, декодувати та виконувати **кілька незалежних команд одночасно за один такт** (наприклад, 2-way або 4-way суперскалярний процесор).

### 4. Що станеться, якщо передбачення переходу виявиться помилковим при спекулятивному виконанні? 
Якщо передбачувач переходів (branch predictor) помилився:
1. Усі спекулятивно виконані або частково оброблені інструкції з хибної гілки **скасовуються** (результати скидаються, зміни в регістри/пам'ять не вносяться).
2. Конвеєр повністю **очищується (flushed)** від завантажених інструкцій.
3. Виконання перезапускається з правильної адреси переходів.  
*Наслідок:* Втрачається кілька робочих тактів процесора (так звана штрафна затримка переходу / branch penalty).


### 5. Сформулюйте суть закону Амдала і його практичний наслідок для багатопоточних програм.
**Відповідь:**  
* **Суть:** Закон Амдала визначає теоретичну межу максимального прискорення програми при її розпаралелюванні. Загальне прискорення обмежене часткою коду $f$, яку необхідно виконувати строго послідовно:

$$S = \frac{1}{f + \frac{1 - f}{p}}$$

*(де $f$ — послідовна частка, $p$ — кількість процесорів/ядер)*.

* **Практичний наслідок:** Нарощування кількості ядер має межу практичної користі (*закон спадної віддачі*). Навіть при нескінченній кількості ядер ($p \to \infty$) прискорення програми не може перевищити $\frac{1}{f}$. Якщо $20\%$ коду послідовні ($f=0.2$), максимальне прискорення ніколи не буде більшим ніж $5\times$.

### 6. Що таке big.LITTLE і навіщо потрібні гетерогенні ядра? 
* **big.LITTLE:** Це архітектура гетерогенних обчислень, що об'єднує на одному кристалі два типи ядер:
  * **"big" (потужні):** Високопродуктивні ядра з високим енергоспоживанням для складних та критичних до швидкості завдань (ігри, обробка відео).
  * **"LITTLE" (енергоефективні):** Простіші та економні ядра для фонових і простіших задач (фонова синхронізація, системні сповіщення).
* **Призначення:** Забезпечення оптимізованого балансу між піковою продуктивністю та тривалістю автономної роботи від батареї в мобільних та вбудованих пристроях.

### 7. Чому пересилання даних (forwarding) дозволяє уникнути зупинки конвеєра при конфлікті за даними, а в яких випадках зупинка (stall) все одно неминуча?
* **Чому допомагає:** Пересилання даних (Data Forwarding / Bypassing) передає обчислений результат безпосередньо з виходу стадії виконання ($E$) одного блоку на вхід стадії $E$ наступної інструкції апаратними каналами, не чекаючи, поки результат буде фізично записаний у регістровий файл на стадії $W$.
* **Коли зупинка неминуча:** При операціях читання з пам'яті (команда `LOAD`). Якщо за командою `LOAD R1, [MEM]` одразу йде команда, що використовує $R1$, дані стають доступними лише наприкінці стадії $M$ (Memory). Оскільки наступній команді вони потрібні вже на початку стадії $E$, виникає необхідність вставити принаймні один такт простою (Load-use hazard stall / bubble).

### 8. Чому теоретичне 4-кратне прискорення від SIMD-інструкції для 4 елементів даних рідко досягається на практиці повністю?
Причини недосяжності пікового прискорення:
1. **Затримки пам'яті:** Потрібен час для завантаження та вирівнювання (alignment) векторних даних у пам'яті.
2. **Накладні витрати:** Наявність накладних команд підготовки, упаковки/розпаковки векторних регістрів та організації циклів.
3. **Обмеження пропускної здатності шини пам'яті:** Виконавчі блоки чекають на підтягування даних з L1/L2/L3 кешу чи RAM.
4. **Невекторизований код:** Частина коду (ініціалізація, обробка залишків елементів) виконується скалярно.

### 9. За формулою закону Амдала: до якого максимального прискорення можна наблизитись, якщо послідовна частка коду f = 0,2, незалежно від кількості ядер?
При спрямуванні кількості ядер $p$ до нескінченності ($p \to \infty$):
$$S_{max} = \frac{1}{f} = \frac{1}{0.2} = 5$$
**Відповідь:** Максимальне теоретичне прискорення становить **5 разів** (або $5\times$).

### Завдання 1. Закон Амдала
**Умова:**  
* Послідовна частка коду $f = 25\% = 0.25$
* Паралельна частка $(1 - f) = 75\% = 0.75$
* Формула: $S = \frac{1}{f + \frac{1 - f}{p}}$

**Обчислення:**
1. **Для $p = 4$ процесорів:**
   $$S_4 = \frac{1}{0.25 + \frac{0.75}{4}} = \frac{1}{0.25 + 0.1875} = \frac{1}{0.4375} \approx 2.2857 \quad (\mathbf{\approx 2.29\times})$$

2. **Для $p = 8$ процесорів:**
   $$S_8 = \frac{1}{0.25 + \frac{0.75}{8}} = \frac{1}{0.25 + 0.09375} = \frac{1}{0.34375} \approx 2.9091 \quad (\mathbf{\approx 2.91\times})$$

3. **Для $p = 16$ процесорів:**
   $$S_{16} = \frac{1}{0.25 + \frac{0.75}{16}} = \frac{1}{0.25 + 0.046875} = \frac{1}{0.296875} \approx 3.3684 \quad (\mathbf{\approx 3.37\times})$$

4. **Граничне прискорення ($p \to \infty$):**
   $$S_{max} = \frac{1}{f} = \frac{1}{0.25} = 4\times$$

**Висновок:**  
Далі нарощувати кількість ядер **не має практичного сенсу**. Збільшення кількості процесорів у 4 рази (із 4 до 16) підвищує продуктивність лише з $2.29\times$ до $3.37\times$ (менш ніж у 1.5 раза), при цьому максимальне можливе прискорення обмежене рівнем $4\times$. Витрати на додаткове обладнання не виправдовують незначного приросту швидкості.

### Завдання 2. Визначення типу конфлікту конвеєра (hazard)
**Псевдокод:**
```assembly
ADD R1, R2, R3 ; R1 = R2 + R3
SUB R4, R1, R5 ; R4 = R1 - R5

```

**Визначення типу конфлікту:**

Це **конфлікт за даними (Data Hazard)**, а саме залежність типу *Read-After-Write (RAW)*.

**Пояснення:**

У 5-стадійному конвеері (*Fetch-Decode-Execute-Memory-Write*):

1. Інструкція `ADD` обчислює нове значення $R1$ на стадії **Execute (E)** (3-й такт) і записує його у регістровий файл лише на стадії **Write-back (W)** (5-й такт).
2. Наступна інструкція `SUB` іде одразу за `ADD` i зчитує значення регістрів на своїй стадії **Decode (D)** (3-й такт).
3. Оскільки на 3-му такті `ADD` ще не дійшла до стадії $W$, інструкція `SUB` зчитає **застаріле значення** $R1$ з регістрового файлу, що призведе до неправильних обчислень.

### Завдання 3. Приклад коду з умовним переходом

**Приклад коду (псевдокод / C):**

```c
if (x > 0) {
    y = y + 1; // Гілка A
} else {
    y = y - 1; // Гілка B
}

```

**Пояснення, чому створюється конфлікт за керуванням (Control Hazard):**

Процесор завантажує інструкції в конвеєр на стадії *Fetch (F)* послідовно. Однак умова `x > 0` обчислюється лише на стадії *Execute (E)*. Поки умова обчислюється, процесор не знає, яку саме інструкцію потрібно завантажувати наступною — виконання гілки A чи гілки B. Якщо процесор продовжить завантажувати інструкції наосліп або припуститься помилки в передбаченні, йому доведеться скасувати виконання й очистити конвеєр, що створює затримки.
