### Запитання 1. У чому різниця між доставкою «від вузла до вузла» і «від процесу до процесу»?

Мережевий рівень (network layer) працює за принципом **«від вузла до вузла» (host-to-host)**: IP-адреса ідентифікує лише пристрій у мережі, і маршрутизатори доставляють пакет саме на цей пристрій. Проте на одному вузлі одночасно працює багато процесів (браузер, поштовий клієнт, сервер бази даних), тому однієї IP-адреси недостатньо — потрібно знати, якому саме процесу призначені дані.

Цю задачу розв'язує транспортний рівень (transport layer), який забезпечує доставку **«від процесу до процесу» (process-to-process)** за допомогою номерів портів.

| Критерій | Від вузла до вузла (host-to-host) | Від процесу до процесу (process-to-process) |
|---|---|---|
| Рівень | мережевий (network layer) | транспортний (transport layer) |
| Ідентифікатор | IP-адреса | номер порту (0–65535) |
| Що визначає | пристрій (вузол) у мережі | конкретний процес або службу на вузлі |
| Одиниця даних | пакет | сегмент (TCP) або датаграма (UDP) |
| Приклад | `192.168.1.20` | порт `443` — веб-сервер, порт `22` — SSH |

**Механізм роботи.** На стороні відправника відбувається *мультиплексування*: дані від різних процесів (з різними портами джерела) передаються через один мережевий рівень. На стороні отримувача — *демультиплексування*: за портом призначення операційна система передає дані саме тому процесу, який слухає цей порт.

Додатково транспортний рівень, залежно від протоколу, забезпечує надійність, впорядкування та керування потоком (TCP) або не забезпечує їх (UDP).

### Запитання 2. Що таке сокет і з яких компонентів він складається?

**Сокет (socket)** — це пара **«IP-адреса + номер порту»**, яка однозначно визначає кінцеву точку з'єднання.

Компоненти сокета:

1. **IP-адреса** — визначає вузол у мережі.
2. **Номер порту** (0–65535) — визначає процес або службу на цьому вузлі.

Приклад сокета: `93.184.216.34:443`.

**З'єднання** між клієнтом і сервером визначається **парою сокетів**:

```
(адреса клієнта : порт клієнта)  <->  (адреса сервера : порт сервера)
(192.168.1.10 : 51034)           <->  (93.184.216.34 : 443)
```

Завдяки цьому один серверний сокет (наприклад, порт 443) може одночасно обслуговувати багато клієнтів: їхні сокети відрізняються IP-адресою або портом клієнта, тому кожне з'єднання однозначне.

Порт і протокол (TCP або UDP) разом однозначно визначають сокет, тому TCP-порт 6000 і UDP-порт 6000 — це різні сокети, які можуть існувати одночасно.

Діапазони портів:

| Діапазон | Назва | Призначення | Приклади |
|---|---|---|---|
| 0–1023 | well-known (добре відомі) | стандартні служби | 80 (HTTP), 443 (HTTPS), 22 (SSH), 53 (DNS) |
| 1024–49151 | registered (зареєстровані) | реєструються за застосунками, не потребують привілеїв | 6000–6111 (практичне заняття №10) |
| 49152–65535 | dynamic / private (динамічні) | тимчасово виділяються клієнтським застосункам | вихідний порт браузера |

### Запитання 3. Опишіть послідовність триетапного рукостискання TCP

З'єднання TCP встановлюється **триетапним рукостисканням (three-way handshake)**. Мета — узгодити початкові номери послідовності (initial sequence number) обох сторін і переконатися, що зв'язок працює в обох напрямках.

```
 Клієнт                                         Сервер
   |                                               |
   | ---- SYN (seq=x) ------------------------->   |   крок 1
   |                                               |
   | <--- SYN-ACK (seq=y, ack=x+1) -------------   |   крок 2
   |                                               |
   | ---- ACK (seq=x+1, ack=y+1) -------------->   |   крок 3
   |                                               |
   |            з'єднання встановлено              |
```

**Числовий приклад** (початковий `seq` клієнта — 5000, сервера — 8000):

| Крок | Напрямок | Прапорці | seq | ack |
|---|---|---|---|---|
| 1 | клієнт → сервер | SYN | 5000 | — |
| 2 | сервер → клієнт | SYN, ACK | 8000 | 5001 |
| 3 | клієнт → сервер | ACK | 5001 | 8001 |

**Пояснення кроків:**

1. **SYN.** Клієнт ініціює з'єднання: встановлює прапорець `SYN` і передає свій початковий `seq`.
2. **SYN-ACK.** Сервер підтверджує байт клієнта (`ack = seq клієнта + 1`) і водночас передає власний початковий `seq` (прапорці `SYN` та `ACK`).
3. **ACK.** Клієнт підтверджує `seq` сервера таким самим способом (`ack = seq сервера + 1`).

Прапорець `SYN` «витрачає» один номер послідовності, тому підтвердження дорівнює `seq + 1`. Після третього кроку обидві сторони знають початкові номери одна одної та можуть передавати дані.

### Запитання 4. Як ковзне вікно та повторна передача за таймаутом забезпечують надійність TCP?

**Ковзне вікно (sliding window)** дозволяє відправнику надсилати кілька сегментів, не чекаючи підтвердження на кожен. Обсяг непідтверджених даних обмежений розміром вікна отримувача (поле `window size` у заголовку TCP). Коли надходить підтвердження, вікно «зсувається» вперед і дозволяє надіслати нові дані. Таким чином вікно одночасно забезпечує **керування потоком**: відправник не перевантажує отримувача.

**Повторна передача за таймаутом (retransmission on timeout).** Після надсилання сегмента відправник запускає таймер. Якщо підтвердження не надійшло до його спливання (`timeout`), сегмент передається повторно.

**Номери послідовності та підтвердження.** Кожен байт потоку має номер. Отримувач підтверджує дані номером наступного очікуваного байта (`acknowledgment number`). Це дозволяє виявляти втрачені та дубльовані сегменти, а також **відновлювати порядок**: сегменти, що прийшли не за порядком, буферизуються і віддаються застосунку у правильній послідовності.

**Приклад.** `MSS` = 1000 байт, вікно = 3000 байт (до трьох непідтверджених сегментів), початковий `seq` = 1000.

| Крок | Подія |
|---|---|
| 1 | Відправник надсилає три сегменти без очікування підтвердження: `seq=1000`, `seq=2000`, `seq=3000` (кожен — 1000 байт). |
| 2 | Сегмент `seq=2000` втрачено в мережі. Сегмент `seq=1000` дійшов — отримувач надсилає `ack=2000`. |
| 3 | Сегмент `seq=3000` дійшов не за порядком (бракує байтів 2000–2999): отримувач буферизує його, застосунку не віддає і знову надсилає `ack=2000`. |
| 4 | Таймер для сегмента `seq=2000` спливає — відправник передає його повторно. |
| 5 | Отримувач має байти 2000–2999 і буферизовані 3000–3999: віддає застосунку байти 1000–3999 у правильному порядку й надсилає `ack=4000`. |
| 6 | Вікно зсувається, відправник може надсилати сегменти починаючи з `seq=4000`. |

**Результат:** жоден байт не втрачено, не продубльовано й не переставлено — це і є надійна впорядкована доставка.

> **Примітка про пропускну здатність.** Максимальна швидкість TCP-з'єднання обмежена величиною `вікно / RTT`. Для супутникового каналу з `RTT ≈ 600 мс` і вікна 64 КіБ: `65 536 × 8 / 0,6 ≈ 874 000 біт/с ≈ 0,87 Мбіт/с` — незалежно від того, наскільки велика смуга пропускання каналу. Відправник просто чекає підтверджень, поки вікно не «відкриється». (У сучасних реалізаціях TCP опція *window scaling* дозволяє збільшувати вікно понад 64 КіБ, але принцип обмеження залишається.)

### Запитання 5. Чим відрізняються повільний старт і уникнення перевантаження?

Обидва механізми належать до **керування перевантаженням (congestion control)** — обмежують швидкість передачі відповідно до стану мережі, а не лише до можливостей отримувача.

| Критерій | Повільний старт (slow start) | Уникнення перевантаження (congestion avoidance) |
|---|---|---|
| Коли діє | на початку передачі та після втрати, поки вікно менше за поріг `ssthresh` | після досягнення порогу `ssthresh` |
| Зростання вікна | **експоненційне** — подвоєння з кожним RTT | **лінійне** — +1 MSS за RTT |
| Мета | швидко знайти доступну пропускну здатність | обережно наближатися до межі, не перевантажуючи мережу |
| Ризик | швидкий вихід на межу мережі | повільніше зростання швидкості |

**Числовий приклад** (початкове вікно — 1 MSS, `ssthresh` = 16 MSS):

| RTT (раунд) | Вікно перевантаження | Фаза | Приріст |
|---|---|---|---|
| 0 | 1 MSS | slow start | — |
| 1 | 2 MSS | slow start | подвоєння |
| 2 | 4 MSS | slow start | подвоєння |
| 3 | 8 MSS | slow start | подвоєння |
| 4 | 16 MSS | досягнуто `ssthresh` | подвоєння |
| 5 | 17 MSS | congestion avoidance | +1 MSS |
| 6 | 18 MSS | congestion avoidance | +1 MSS |

**Реакція на втрату пакета.** Втрата (таймаут або кілька дублікатів підтверджень) сприймається як ознака перевантаження. `ssthresh` перераховується (як правило, вдвічі менше поточного вікна), а вікно знову скидається до малого значення.

Приклад: втрата на RTT 6 (вікно = 18 MSS) → `ssthresh = 18 / 2 = 9 MSS`, вікно = 1 MSS:

| Раунд після втрати | Вікно | Фаза |
|---|---|---|
| 0 | 1 MSS | slow start |
| 1 | 2 MSS | slow start |
| 2 | 4 MSS | slow start |
| 3 | 8 MSS | slow start |
| 4 | 9 MSS | досягнуто `ssthresh` (у спрощеній моделі зростання обмежене порогом) |
| 5 | 10 MSS | congestion avoidance |
| 6 | 11 MSS | congestion avoidance |

> **Примітка.** Це спрощена модель із лекції. У реальних реалізаціях (RFC 5681) після втрати за *кількома дублікатами підтверджень* спрацьовують механізми швидкої повторної передачі та швидкого відновлення (fast retransmit / fast recovery), і вікно зменшується приблизно вдвічі, а не до 1 MSS. Повне скидання до малого значення відбувається, зокрема, після таймауту.

### Запитання 6. У яких випадках UDP є кращим вибором за TCP і чому?

UDP кращий, коли **актуальність даних важливіша за повноту**, а накладні витрати TCP не виправдані:

1. **Реальний час (DNS-запити, VoIP, відеоконференції).** Краще втратити пакет, ніж чекати на повторну передачу застарілих даних: запізнілий аудіокадр однаково вже нікому не потрібен, а повторна передача лише збільшить затримку.
2. **Мовлення та групова розсилка (broadcast, multicast).** TCP працює лише між двома процесами й не підтримує розсилку багатьом отримувачам одночасно, а UDP — підтримує.
3. **Простий запит–відповідь.** Коли накладні витрати на встановлення з'єднання (три пакети рукостискання) не виправдані для одного невеликого повідомлення (наприклад, DNS-запит).

| Критерій | TCP | UDP |
|---|---|---|
| З'єднання | з установленням з'єднання | без з'єднання |
| Надійність | гарантована доставка | не гарантована |
| Порядок | зберігається | не гарантується |
| Накладні витрати | вищі (заголовок від 20 байт) | мінімальні (заголовок 8 байт) |
| Керування перевантаженням | так | ні |
| Типові застосунки | HTTP/HTTPS, передавання файлів, електронна пошта | DNS-запити, VoIP, відеопотік, ігри реального часу |

> **Застереження.** UDP слід обирати свідомо, а не як спосіб «заощадити» без урахування наслідків втрати пакетів. Якщо застосунку потрібна надійність, її доводиться реалізовувати самостійно понад UDP.

### Запитання 7. Яких полів немає в заголовку UDP порівняно з TCP і чому вони там не потрібні?

Заголовок UDP має лише 8 байт (чотири поля по 2 байти: порт джерела, порт призначення, довжина, контрольна сума). Заголовок TCP — щонайменше 20 байт. У UDP відсутні:

| Поле TCP | Призначення в TCP | Чому не потрібне в UDP |
|---|---|---|
| Sequence number (4 байти) | нумерація байтів потоку, впорядкування | UDP не впорядковує дані: кожна датаграма незалежна від інших |
| Acknowledgment number (4 байти) | підтвердження отриманих даних | UDP не підтверджує доставку й не повторює передачу |
| Прапорці `SYN`, `ACK`, `FIN`, `RST`, `PSH`, `URG` | встановлення, підтвердження й закриття з'єднання, аварійне скидання тощо | UDP не встановлює з'єднання, тому нічого встановлювати чи закривати |
| Window size (2 байти) | керування потоком (ковзне вікно) | UDP не обмежує потік даних і не чекає підтверджень |

**Загальна причина:** у UDP просто немає механізму, якому ці поля були б потрібні. Датаграма йде незалежно від інших, а її доля (дійшла чи ні) застосунку невідома без додаткової логіки понад UDP.

Додатково в TCP є ще службові поля (довжина заголовка, покажчик термінових даних, опції), яких у UDP також немає; поле довжини в UDP, навпаки, є, бо воно вказує розмір заголовка й даних разом.

### Запитання 8. Чому закриття TCP-з'єднання називають «4-way termination», а не просто обміном FIN/ACK?

Тому що **кожен напрямок з'єднання закривається незалежно**. TCP-з'єднання дуплексне: дані йдуть в обидва боки, і кожна сторона окремо повідомляє, що завершила передачу. Тому потрібні **два незалежні обміни FIN/ACK — по одному на кожен напрямок**, тобто чотири сегменти.

```
 Клієнт                                          Сервер
   |                                                |
   | ---- FIN (seq=9000) ------------------------>  |   клієнт закрив свій напрямок
   | <--- ACK (ack=9001) ------------------------   |   сервер підтвердив
   |                                                |
   |        сервер ще може надсилати дані           |
   |                                                |
   | <--- FIN (seq=15000) -----------------------   |   сервер закрив свій напрямок
   | ---- ACK (ack=15001) ----------------------->  |   клієнт підтвердив
```

Послідовність:

1. Клієнт першим завершує свій напрямок передачі (`FIN`, `seq=9000`).
2. Сервер підтверджує (`ACK`, `ack=9001`), але сам ще може продовжувати надсилати дані.
3. Коли сервер завершує свій напрямок, він надсилає окремий `FIN` (`seq=15000`).
4. Клієнт підтверджує (`ACK`, `ack=15001`).

`FIN`, як і `SYN`, «витрачає» один номер послідовності, тому `ack = seq + 1`.

Якщо один бік розірвався аварійно, замість `FIN` протилежна сторона отримає `RST` або зафіксує таймаут.

> **Додатково.** Якщо у сервера немає більше даних для передачі, його `ACK` і `FIN` можуть бути об'єднані в один сегмент, і тоді практично спостерігається три сегменти. Концептуально закриття залишається чотириетапним, бо напрямки закриваються незалежно.

### Запитання 9. Чому порти 6000–6111 у Практичному занятті №10 належать до зареєстрованих, а не до well-known, і як фільтр `tcp.flags.syn == 1` допомагає знайти рукостискання у Wireshark?

#### 9.1. Чому порти 6000–6111 — зареєстровані

Діапазон well-known — 0–1023, а діапазон зареєстрованих — 1024–49151. Порти 6000–6111 потрапляють у другий діапазон, тобто належать до **зареєстрованих (registered)**. Причини, чому для застосунку практичного заняття вибрано саме їх:

- **Well-known-порти (0–1023)** закріплені за стандартизованими службами (HTTP, DNS, SSH тощо), і на більшості ОС для їх прив'язки (`bind`) потрібні права адміністратора.
- **Діапазон 6000–6111 не зайнятий жодною стандартною службою** (окрім історичного X11, що традиційно займає 6000–6063, тому варто уникати перетину з ним) і вільно доступний звичайному користувацькому процесу.
- **Різні порти для TCP- і UDP-варіантів** одного заняття (наприклад, TCP `6000` і UDP `6001` для варіанта 1) дозволяють одночасно тримати обидва сервери на одній машині, оскільки порт і протокол разом однозначно визначають сокет.

#### 9.2. Як фільтр `tcp.flags.syn == 1` допомагає знайти рукостискання

Фільтр відображає лише ті пакети, у яких встановлено прапорець `SYN`. Рукостискання починається з пакета з цим прапорцем, тому фільтр одразу показує початок кожного нового TCP-з'єднання серед великого захоплення.

Важливо: прапорець `SYN` встановлений **і в першому пакеті (`SYN`), і в другому (`SYN-ACK`)**, тому фільтр знайде обидва.

| Мета | Фільтр Wireshark | Пояснення |
|---|---|---|
| Усі пакети з `SYN` (кроки 1 і 2) | `tcp.flags.syn == 1` | знаходить і `SYN`, і `SYN-ACK` |
| Лише перший пакет клієнта | `tcp.flags.syn == 1 and tcp.flags.ack == 0` | відсікає `SYN-ACK` |
| Рукостискання на порту застосунку | `tcp.port == 6000 and tcp.flags.syn == 1` | комбінація порту й прапорця |
| Весь обмін по TCP-порту | `tcp.port == 6000` | рукостискання, дані, закриття |
| Весь обмін по UDP-порту | `udp.port == 6001` | датаграми без рукостискання — відсутність `SYN` |
| Аварійний розрив | `tcp.flags.reset == 1` | пакети `RST` |

Для UDP-обміну фільтр `tcp.flags.syn == 1` нічого не покаже — це наочно підтверджує, що UDP працює без встановлення з'єднання.

##  Домашнє завдання

### Завдання 1. Триетапне рукостискання TCP (клієнт: `seq` = 1000, сервер: `seq` = 2000)

| Крок | Напрямок | Прапорці | seq | ack |
|---|---|---|---|---|
| 1 | клієнт → сервер | `SYN` | 1000 | — (прапорець `ACK` не встановлено, поле не використовується) |
| 2 | сервер → клієнт | `SYN`, `ACK` | 2000 | 1001 |
| 3 | клієнт → сервер | `ACK` | 1001 | 2001 |

```
 Клієнт                                         Сервер
   |                                               |
   | ---- SYN (seq=1000) ---------------------->   |   крок 1
   |                                               |
   | <--- SYN-ACK (seq=2000, ack=1001) ---------   |   крок 2
   |                                               |
   | ---- ACK (seq=1001, ack=2001) ------------>   |   крок 3
   |                                               |
   |            з'єднання встановлено              |
```

**Обґрунтування значень:**

- **Крок 1.** Клієнт ініціює з'єднання, тому встановлює `SYN` і передає початковий `seq = 1000`. Підтверджувати ще нічого, тому `ACK` не встановлено.
- **Крок 2.** Сервер підтверджує `SYN` клієнта: `ack = 1000 + 1 = 1001` (`SYN` займає один номер послідовності). Одночасно сервер передає власний початковий `seq = 2000` та встановлює `SYN`.
- **Крок 3.** Клієнт підтверджує `SYN` сервера: `ack = 2000 + 1 = 2001`. Власний `seq` клієнта збільшився на 1 і дорівнює `1001` — це збігається зі значенням `ack` із кроку 2.

**Результат:** перший байт даних клієнта матиме `seq = 1001`, перший байт даних сервера — `seq = 2001`.

### Завдання 2. Вибір між TCP і UDP для чотирьох сценаріїв

| Сценарій | Протокол | Ключова причина |
|---|---|---|
| Завантаження вебсторінки | **TCP** | потрібна повна й точна доставка без втрат |
| VoIP-телефонія | **UDP** | важлива мала затримка, а не повнота |
| Онлайн-гра в реальному часі | **UDP** | застарілі дані марні, важлива швидкість |
| Передача файлу по FTP | **TCP** | потрібна цілісність файлу |

#### 2.1. Завантаження вебсторінки — TCP

- Вебсторінка (HTML, CSS, JavaScript, зображення) має прийти **повністю, без втрат і в правильному порядку**: втрата або перестановка навіть кількох байтів зіпсує розмітку чи скрипт.
- HTTP/HTTPS традиційно працюють поверх TCP (порти 80 і 443): TCP гарантує повторну передачу втрачених сегментів і впорядкування.
- Затримка на рукостискання компенсується повторним використанням з'єднань (keep-alive, пули з'єднань).
- Керування потоком і перевантаженням TCP дозволяє справедливо ділити мережу між багатьма користувачами.

> **Нюанс.** Новіший протокол HTTP/3 працює поверх QUIC, який використовує UDP. Проте надійність і впорядкування там реалізовані самим QUIC у просторі користувача, тобто вимога надійності залишається — змінюється лише місце її реалізації.

#### 2.2. VoIP-телефонія — UDP

- Для розмови в реальному часі критична **низька затримка**. Аудіопакет, що прийшов із запізненням, уже не потрібен — він «пропустив» свій момент відтворення.
- Повторна передача (TCP) лише збільшує затримку й джиттер; втрата одного пакета (десятки мілісекунд звуку) майже непомітна, бо кодеки маскують її.
- TCP міг би «заблокувати» всі наступні пакети в очікуванні одного втраченого (head-of-line blocking), що спричинило б паузи в розмові.
- У UDP мінімальні накладні витрати (заголовок 8 байт), що важливо для невеликих аудіопакетів. Порядок і синхронізацію за потреби забезпечує протокол прикладного рівня (RTP із номерами послідовності й часовими мітками) і буфер джиттера.

#### 2.3. Онлайн-гра в реальному часі — UDP

- Стан гри (позиції гравців, дії) оновлюється десятки разів на секунду. **Старе оновлення втрачає сенс**, щойно надійшло нове, тому повторно передавати втрачений пакет немає потреби.
- Низька затримка (ping) важливіша за гарантовану доставку; TCP через повторні передачі й очікування підтверджень створює відчутні «лаги».
- Мінімальні накладні витрати UDP дозволяють часто надсилати невеликі пакети.
- Якщо для окремих подій потрібна надійність (чат, покупки, результат раунду), її реалізують на рівні застосунку понад UDP або використовують окреме TCP-з'єднання для таких даних.

#### 2.4. Передача файлу по FTP — TCP

- Головна вимога — **цілісність файлу**: втрата або переставлення байтів зробить файл непридатним (пошкоджений архів, виконуваний файл тощо).
- Протокол FTP визначено поверх TCP (керуюче з'єднання — порт 21, передача даних — порт 20 в активному режимі).
- TCP гарантує доставку, повторно передаючи втрачені сегменти, і зберігає порядок байтів.
- Затримка не критична, а ось коректність і повнота — так; керування потоком і перевантаженням захищає від перевантаження отримувача й мережі.

### Завдання 3. DevTools: пошук поля Remote Address

#### 3.1. Порядок виконання

1. Відкрито вебсторінку в браузері за протоколом HTTPS.
2. За допомогою клавіші **F12** відкрито інструменти розробника (**DevTools**).
3. На вкладці **Network** оновлено сторінку за допомогою **F5**, щоб відобразити мережеві запити.
4. Вибрано запит до основного документа сторінки.
5. У деталях запиту відкрито вкладку **Headers** та знайдено поле **Remote Address** у розділі **General**.
6. Зафіксовано IP-адресу віддаленого сервера та порт з'єднання.

#### 3.2. Результат

Поле **Remote Address** відображає IP-адресу віддаленого сервера та порт, через який встановлено мережеве з'єднання.

Приклад для IPv4:

```text
Remote Address: 172.66.164.200:443
```

Приклад для IPv6:

```text
Remote Address: [2001:db8::25]:443
```

**Пояснення:** порт `443` використовується для HTTPS-з'єднань. Значення `Remote Address` залежить від вебсайту, DNS-резолвінгу, мережевої конфігурації та використання проксі-серверів або CDN.



## Підготовка до наступного заняття

**Як браузер дізнається IP-адресу за доменним іменем?** За допомогою системи доменних імен **DNS**:

1. Браузер перевіряє власний кеш, потім кеш операційної системи й файл `hosts`.
2. Якщо запису немає, ОС надсилає **DNS-запит** рекурсивному DNS-серверу (адреса надається, наприклад, за DHCP). Запит зазвичай передається по **UDP, порт 53** — це типовий приклад простого запиту–відповіді, де UDP виправданий.
3. Рекурсивний сервер за потреби опитує кореневі, TLD- та авторитетні DNS-сервери й повертає IP-адресу (записи `A` для IPv4, `AAAA` для IPv6).
4. Отримавши IP-адресу, браузер розпочинає TCP-рукостискання з цією адресою і портом (наприклад, 443).

**Що станеться, якщо DNS-сервер не відповість?**

1. UDP не гарантує доставку, тому надійність забезпечує сам застосунок: запит чекає відповіді **певний час (таймаут)** і **повторюється**.
2. Після невдалих спроб клієнт переходить до **резервного (вторинного) DNS-сервера**, якщо він налаштований.
3. Якщо відповіді немає від жодного сервера, ім'я **не буде перетворене в IP-адресу**. Браузер не зможе навіть почати TCP-рукостискання (немає адреси призначення) і покаже помилку на кшталт `ERR_NAME_NOT_RESOLVED` або `DNS_PROBE_FINISHED_NO_INTERNET` (Chrome).
4. Сторінка при цьому недоступна, хоча сам сервер сайту може працювати — проблема на етапі розв'язання імені.

Додатково: якщо відповідь DNS завелика для однієї UDP-датаграми, використовується TCP (порт 53). Ця тема розкривається в Лекції №18.



## Висновки

1. Транспортний рівень доповнює доставку «від вузла до вузла» мережевого рівня доставкою **«від процесу до процесу»** за допомогою портів; сокет (IP-адреса + порт) однозначно визначає кінцеву точку з'єднання.
2. **UDP** — мінімалістичний протокол без з'єднання й гарантій (заголовок 8 байт); його варто обирати, коли актуальність даних важливіша за повноту (реальний час, групова розсилка, простий запит–відповідь).
3. **TCP** гарантує надійну впорядковану доставку потоку байтів завдяки номерам послідовності й підтвердження, прапорцям, ковзному вікну й повторній передачі; заголовок — щонайменше 20 байт.
4. З'єднання TCP встановлюється **триетапним рукостисканням** (`SYN`, `SYN-ACK`, `ACK`), а закривається **чотириетапно**, бо кожен напрямок закривається незалежно.
5. **Керування перевантаженням** (повільний старт, уникнення перевантаження, реакція на втрату) обмежує швидкість відправника відповідно до стану мережі.
6. Фільтри Wireshark (`tcp.flags.syn == 1`, `tcp.port == 6000`, `udp.port == 6001`) дозволяють наочно порівняти TCP- та UDP-обмін: TCP витрачає щонайменше три пакети на рукостискання й щонайменше два на закриття, UDP одразу передає датаграму з даними.
